# Build diagnosis

## Failure boundaries

The fresh reproductions of the supplied command workflows expose downstream configure and link failures across three producer-metadata contracts and two install layouts, not defects in the C implementation. The first is a link failure: the package never creates the `cjson_utils-static` imported target, so CMake treats that identifier as the raw linker name `-lcjson_utils-static`. The archives exist under deliberately preserved output names, which rules out a producer compile failure.

The fresh relocation reproductions fail earlier, during downstream CMake configuration. Their generated import file references `/tmp/package-stage-a` after that staging prefix was removed. The `.pc` query independently emits include and library flags rooted at the removed prefix, causing the compiler to miss a public header. A successful producer build and package discovery therefore do not close either consumption contract. The second relocation deliberately uses the multi-component library directory `lib/x86_64-linux-gnu` and the selected include directory `include/sdk`; a fixed number of parent traversals that only fits `lib/pkgconfig` would misidentify `<moved-prefix>/lib` as the package prefix in that layout; the resulting include and library flags then point below lib rather than to the actual prefix and the consumer cannot find its headers or libraries.

## Owning declarations and repair

The static targets were installed as files but omitted from the export sets; `cjson_utils-static` transitively links `cjson-static`, so both public target identifiers must be exported together while their output names stay stable. Separately, absolute `CMAKE_INSTALL_FULL_*` destinations capture the removed staging prefix in generated import metadata. Relative GNUInstallDirs destinations allow CMake's generated `_IMPORT_PREFIX` to follow the current package location. For the legacy variables, `configure_package_config_file` derives `PACKAGE_PREFIX_DIR` from the configured install destination and expands the selected include directory through `PATH_VARS`; this relationship makes CJSON_INCLUDE_DIRS point to the relocated include/sdk directory even when the library directory has more than one path component.

The two pkg-config templates are a metadata contract separate from the CMake exports. Their stale include and library flags point to the removed prefix; their prefix is now derived from `${pcfiledir}`. The producer computes `CJSON_PC_PREFIX` as the relative path from the actual `${CMAKE_INSTALL_LIBDIR}/pkgconfig` install location back to the prefix, while the templates preserve the configured relative `libdir` and `includedir` names. The existing `Requires: libcjson` dependency declaration and core `Libs.private: -lm` edge remain unchanged. Editing a consumer search path, renaming archives, or patching generated metadata would only hide the producer defect. The patch preserves public target identifiers, archive output names, shared library behavior, and all implementation/header bytes.

## Evidence closure and limits

Validation starts from fresh producer copies and staging prefixes, moves each installed tree, deletes each original prefix, and uses only the moved package. The default layout has independent CMake shared-core and static-utility consumers plus a pkg-config consumer. The multi-component library layout checks the legacy CMake include variable, builds and runs the static target, and queries, builds, and runs through pkg-config. This smoke scope establishes the captured configure/link/load paths and two requested layouts, not general ABI compatibility, alternate generators, platforms, or untested package-manager conventions.

The original evidence bundle supplied commands but omitted historical stdout/stderr. `failure/fresh-reproduction.json` contains newly executed commands, exit statuses, output and source hashes; these are fresh local reproductions, not recovered historical records.
